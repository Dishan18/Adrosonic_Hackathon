The system is built on a hybrid deterministic/agentic philosophy: AI and heuristics suggest and map, but strictly whitelisted Python/Pandas functions execute changes with 100% human auditability.

2. System Architecture

The system follows an asynchronous, pipeline-driven architecture divided into five modular layers:

Layer 1: Ingestion
Workbook Processing
OpenPyXL parses multi-sheet Excel/CSV workbooks, unmerges merged title cells, and detects tabular boundaries.
Layer 2: Intelligence
Multi-Agent Cascade
Discovery, 4-stage Schema Mapping, and Quality Reasoning agents generate confidence-scored proposals.
Layer 3: Human Gate
HITL Approval Barrier
Streamlit review console forces underwriting validation for low-confidence or critical mapping decisions.
Layer 4: Execution
Controlled Transformation
Deterministic transformation whitelist runs approved mutations and logs every cell change to an audit trail.
Layer 5: Deliverables
Pandera & Export
Output verified against exact 17-column schema and exported as Cleaned_SOV.xlsx and Audit_Log.xlsx.
Core Architectural Invariant: The LLM is never permitted to directly alter raw tabular cell data. All data mutations are performed by audited, pure Python functions strictly tied to an approved recommendation ID.

3. The 4-Agent Pipeline in Detail

Agent 1: Sheet Discovery & Header Detection (sheet_discovery.py)

Commercial SOVs frequently arrive with preamble metadata, cover letters, legal disclaimers, or multi-sheet workbooks. This agent scans all sheets and locates the true tabular header row.

  • Multi-Factor Sheet Scoring: Evaluates sheet name relevance, row/col density, keyword overlap against insurance terms (e.g. Building, Occupancy, TIV, Address), and string/numeric ratios.
  • Header Row Search: Scans rows 0 through 15 calculating header density, string-to-number ratio, and non-empty column span to isolate the exact header row while skipping decorative titles.
  • Classification: Categorizes sheets into PRIMARY, SECONDARY, or EXCLUDED.

Agent 2: Cascading Schema Mapping (schema_mapping.py)

Maps arbitrary source column headers to the 17 standardized canonical fields using a rigorous 4-stage cascade:

Stage 1: Memory
ChromaDB Recall
Exact match on past human-approved mappings. (Confidence = 1.0)
Stage 2: Exact Match
Lexical Matching
Normalized string comparison against field names and curated aliases. (Confidence = 1.0)
Stage 3: Fuzzy Match
RapidFuzz Token Set
Levenshtein similarity ratio $\ge 0.82$ against target aliases. (Confidence = 0.82 - 0.95)
Stage 4: Semantic
BGE Small Embeddings
Dense cosine similarity between source column name + sample values and target field semantics. (Confidence = 0.70 - 0.90)

Constraint Enforcement: A greedy 1-to-1 matching algorithm guarantees that no two input columns are assigned to the same target field.

Agent 3: Data Quality Reasoning & HITL Generation (quality_reasoning.py)

Performs statistical profiling, anomaly detection, and human review recommendation synthesis.

  • Heuristic Profiling: Detects currency formatting ($ symbols, commas), state spellings, non-integer years, invalid sprinkler codes, and empty values.
  • Quality Scoring: Computes a standardized dataset score (0 to 100) factoring completeness, schema compliance, validity, and consistency.
  • Automated LLM Synthesis: Leverages the Groq LLM Gateway to generate structured, human-readable underwriting explanations ("Why this change is needed", "Impact on portfolio modeling").
  • HITL Review Requirement: If confidence is < 90% or if the operation involves field renaming or schema ambiguity, review_required=True locks the transformation gate until confirmed.

Agent 4: Controlled Transformation & Pandera Validation (transformation.py)

Executes approved recommendations with mathematical determinism.

  • Whitelisted Mutations: Strictly limited to safe operations: strip_currency, to_float, to_int, to_year_int, normalize_state, normalize_sprinkler_code, column_rename.
  • Null Preservation: Missing/blank values are strictly preserved as NaN or empty strings—the system never synthesizes fake property values.
  • Schema Contract: Ensures output has exactly the 17 target columns in the canonical order.
  • Pandera Enforcement: Runs runtime DataFrame validation verifying column types and constraints.
  • Audit Logging: Logs every cell transformation into an immutable, downloadable audit trail.

7. Putting Into Production & Scaling Strategies

To scale this system from hackathon demo to an enterprise-grade commercial underwriting platform processing tens of thousands of complex property schedules monthly, implement the following architectural enhancements:

A. Microservices Decoupling (API & Worker Separation)

  • FastAPI Core Service: Replace direct Streamlit processing with a high-throughput async FastAPI gateway exposing /api/v1/sov/upload, /api/v1/sov/{id}/status, /api/v1/sov/{id}/approve, and /api/v1/sov/{id}/export.
  • Celery + Redis Task Workers: Offload heavy workbook parsing, embedding generation, and Pandera validations to distributed Celery workers running on containerized worker nodes (AWS ECS / Kubernetes).
  • WebSocket Real-Time Progress: Stream pipeline stage updates (Discovery → Mapping → Quality) to the frontend via WebSockets instead of blocking HTTP requests.

B. Distributed Vector Store & Relational State Management

  • PostgreSQL + pgvector: Replace local embedded ChromaDB with managed PostgreSQL using the pgvector extension. Store both relational session state (audits, recommendations, user approvals) and 384-d semantic column embeddings in a single ACID-compliant database.
  • Tenant Isolation: Partition episodic mapping memory by broker_id or carrier_id so firm-specific synonyms (e.g. Aon vs. Marsh naming conventions) are recalled accurately without cross-tenant bleed.

C. High-Performance Caching & Cost Optimization

  • Exact Header Redis Cache: Cache MD5 hashes of row-0 headers. If an identical broker spreadsheet layout is processed again, retrieve 100% of mappings in < 5ms with zero LLM API or embedding costs.
  • Selective LLM Invocation: Retain the current design where 90%+ of mappings are solved deterministically via Memory, RapidFuzz, and Cosine similarity. Only route unresolved anomalies or edge-case occupancy reclassification to the LLM Gateway.

D. Enterprise Security, Auditing & Compliance

  • S3 / Azure Blob Storage with KMS Encryption: Store uploaded raw files and finalized Cleaned_SOV.xlsx files in private object stores encrypted at rest via AWS KMS (AES-256).
  • Immutable Tamper-Evident Audit Trails: Export audit log entries with SHA-256 hash chains to satisfy internal model governance and external insurance regulator examinations (NAIC / Lloyd's compliance).
  • PII Redaction: Strip individual property owner names or contact phone numbers prior to any third-party LLM inference.

8. Comprehensive Interview Questions & Technical Deep-Dive

A curated set of challenging questions frequently asked by technical interviewers, system architects, and hiring managers regarding this system's design, algorithmic trade-offs, and implementation details.

Category A: Multi-Agent Architecture & LangGraph Design

Q1: Why did you choose an Agentic / Multi-Agent architecture instead of a single prompt sending the entire spreadsheet to GPT-4o or Claude 3.5 Sonnet?

Evaluation Target: Context window costs, hallucination control, latency, and determinism

Model Answer:

In commercial insurance underwriting, using an LLM as a monolithic end-to-end data transformer is fundamentally flawed for four primary reasons:

  • Hallucination & Numerical Integrity: LLMs are autoregressive token predictors, not execution engines. Asking an LLM to rewrite thousands of rows containing Building Values (e.g. $45,230,000) risks subtle token mutations, row dropouts, or synthetic value fabrication, which creates catastrophic underwriting exposure errors.
  • Context Window & Cost Explosion: Production SOVs easily exceed 10,000 rows. Sending entire raw tables to frontier models consumes millions of tokens, triggering exorbitant API bills and multi-minute response latencies.
  • Separation of Concerns: Our multi-agent system decouples Discovery (structural layout), Mapping (lexical & semantic alignment), Quality Reasoning (business rule audit), and Transformation (deterministic execution). Each agent has a single, verifiable responsibility.
  • Deterministic Sandbox: In our system, the LLM is restricted strictly to an advisory role (reasoning and selecting whitelisted functions). Only pre-validated, pure Python routines ever mutate cell data.

Q2: How does your LangGraph state container enforce immutability and handle state rollbacks on failure?

Evaluation Target: Distributed state design, Pydantic V2 deep copying, error recovery

Model Answer:

Every LangGraph node function in app/agents/ receives a typed SOVState instance and immediately executes state = state.model_copy(deep=True) before performing any mutations. This guarantees that:

  • No agent inadvertently mutates previous stage snapshots via reference sharing.
  • If an unhandled exception or Pandera schema validation failure occurs in Agent 4, the system captures the failure state in state.stage = WorkflowStage.ERROR or WorkflowStage.VALIDATING without corrupting intermediate mapping or profiling states.
  • The human reviewer can interactively adjust, reject, or override recommendations without requiring the system to re-run expensive sheet discovery or vector embedding computations from scratch.

Category B: Schema Mapping, NLP & Vector Retrieval

Q3: Walk me through your 4-Tier Schema Mapping cascade. Why not use vector search for all columns?

Evaluation Target: Latency hierarchies, algorithmic efficiency, semantic false positives

Model Answer:

Vector search is computationally heavier (~5–10ms per query) and is prone to semantic false positives on domain-specific acronyms. Our 4-tier cascade implements a strict efficiency and precision hierarchy:

  • Tier 0 (ChromaDB Memory): Checked first. If a broker previously submitted column "Loc Bldg Identifier" and an underwriter approved it to Reference, vector memory returns this in < 2ms with an approved memory confidence multiplier (1.10x).
  • Tier 1 (Exact Normalized Hash): $O(1)$ hash table lookup against 17 canonical names and 80+ standard insurance synonyms. Resolves ~60% of columns in microseconds with 0.97 confidence.
  • Tier 2 (RapidFuzz Token Sort Ratio): Handles minor typos, punctuation differences, and word re-orderings (e.g. "Values - Building" vs "Building Values"). Threshold cutoff is set at 78%.
  • Tier 3 (Dense BGE Embeddings): Evaluates cosine similarity using BAAI/bge-small-en-v1.5 (384 dimensions) against canonical definitions. Handles semantic synonyms like "Time Element" ↔ BI.
  • Tier 4 (LLM Gateway): Invoked only if prior tiers fail or produce conflicting signals. The LLM receives masked sample rows and candidate targets, returning a strictly structured JSON decision.

Q4: What is the Hungarian Conflict Resolution algorithm, and why is it necessary in SOV cleansing?

Evaluation Target: Bipartite matching, 1:1 constraints, collision prevention

Model Answer:

In real-world broker files, multiple raw columns frequently show high similarity to the same canonical target. For example, a workbook may contain both Building Limit and Building Notes. A naive mapper could map both to Building Value, corrupting the downstream underwriting feed.

Our Hungarian assignment step enforces a strict 1:1 injective target constraint:

  • Groups all source column mappings by target field.
  • If $|C_{\text{target}}| > 1$, evaluates their calibrated multi-modal confidence scores ($W_{\text{name}} \cdot S_{\text{name}} + W_{\text{value}} \cdot V_{\text{profile}} + W_{\text{method}} \cdot A_{\text{method}}$).
  • Assigns the target exclusively to the maximum-confidence column: $C^* = \arg\max_i \text{Confidence}(C_i \to T)$.
  • Demotes all competing columns to UNRESOLVED with confidence 0.0 and logs an explicit demotion rationale in the audit trail.

Q5: What is "Value Profile Fit" (VPF) and how does it prevent catastrophic mapping errors?

Evaluation Target: Multi-modal signal fusion, data distribution profiling, defensive AI

Model Answer:

Relying purely on column header names is dangerous because brokers use misleading or overloaded labels. For example, a column labeled "State" could contain building status descriptions ("Under Construction", "Vacant") rather than geographic US state abbreviations ("CA", "TX"). Conversely, a column labeled "Coverage 1" might contain dollar amounts ($2,500,000).

The profiling.py module inspects actual cell data:

  • Computes numeric ratio, currency ratio, date/year patterns, 5-digit ZIP codes, and 2-letter postal codes.
  • score_value_profile_fit(profile, target) produces a score from 0.0 to 1.0.
  • If a column labeled "State" has zero 2-letter state codes and a 95% numeric ratio, its VPF for State collapses to 0.0. In the confidence formula ($0.45 S_{\text{name}} + 0.35 V_{\text{profile}} + 0.20 A_{\text{method}}$), this drop pulls the total confidence below the 0.50 threshold, routing the column to human review rather than silently corrupting the dataset.

Category C: Data Engineering, Resiliency & Edge Cases

Q6: How do you handle merged cells, forward filling, and multi-tier headers in OpenPyXL?

Evaluation Target: Low-level spreadsheet parsing, Excel object model

Model Answer:

Standard pd.read_excel() fails on complex merged headers because it places the cell value in the top-left coordinate and leaves all other spanned coordinates as NaN. Our unmerge_and_forward_fill() implementation handles this cleanly:

  1. Opens the workbook using openpyxl.load_workbook(path, data_only=True) to capture calculated formula results rather than raw formula text strings.
  2. Extracts all range coordinates from worksheet.merged_cells.ranges.
  3. For each range $(r_{\min}, c_{\min}) \dots (r_{\max}, c_{\max})$, reads the master value at $(r_{\min}, c_{\min})$.
  4. Unmerges the range via worksheet.unmerge_cells() and writes the master value into every sub-cell across both rows and columns.
  5. Passes the sanitized grid to pandas, preserving parent category names across sub-columns.

Q7: You encountered a pandas AttributeError: 'DataFrame' object has no attribute 'str' during production testing. What caused it and how did you resolve it?

Evaluation Target: Real-world debugging, Pandas internal mechanics, DataFrame vs Series slicing

Model Answer:

In broker file SOV_B4ID.xlsx, three separate columns shared the exact same header: "2024 - Increase 10%". In pandas, slicing df[col] returns a pd.Series if col is unique, but returns a 2D pd.DataFrame if col appears multiple times.

Downstream profiling code called series.dropna().astype(str).str.strip(). Calling .str on a DataFrame raises AttributeError because .str is an accessor exclusive to Series.

The Fix:

  • In workbook.py::extract_data_frame(), implemented automatic header deduplication during initial extraction (appending _1, _2 suffixes to duplicate names).
  • In profiling.py::profile_column() and schema_mapping.py::map_column(), added defensive type checks: if isinstance(series, pd.DataFrame): series = series.iloc[:, 0].
  • In transformation.py, disambiguated duplicate target columns by calculating non-null counts across candidate slices and preserving the slice with the highest information density.

Category D: Scalability, Productionization & LLM Failovers

Q8: How does your system behave when cloud LLM rate limits (e.g. Groq TPM limits) or network outages occur?

Evaluation Target: High availability, circuit breakers, graceful degradation

Model Answer:

The system implements a multi-provider fallback hierarchy inside app/services/llm/gateway.py:

  • Gateway Client Abstraction: Code interacts with get_llm() rather than calling provider-specific SDKs directly.
  • Automatic Local Failover: If the primary provider (e.g. Groq) encounters an HTTP 429 (Rate Limit Exceeded) or connection timeout, the gateway falls back immediately to local Ollama running mistral:latest on port 11434.
  • Safe Degradation: If local Ollama is also unavailable or times out, the pipeline does not crash. It gracefully demotes unresolved columns to UNRESOLVED, flags them for human review, and continues executing all deterministic mappings and Pandera validations.

Q9: How would you scale this application to process 50,000 SOVs per day in an enterprise insurance carrier?

Evaluation Target: System design, distributed systems, queuing, database partitioning

Model Answer:

To transition from the current single-instance Streamlit app to an enterprise underwriting fabric:

  • Decouple Frontend & Backend: Expose async REST APIs via FastAPI (e.g., POST /api/v1/sov/ingest, GET /api/v1/sov/{id}/status, POST /api/v1/sov/{id}/decide). Stream real-time stage progress to client SPAs via WebSockets.
  • Distributed Task Workers (Celery + Redis): Enqueue incoming workbooks onto Redis task queues. Stateless Celery worker pods deployed on AWS EKS or ECS handle unmerging, embedding generation, and Pandera validation horizontally.
  • Database Migration (PostgreSQL + pgvector): Replace local ChromaDB with a centralized PostgreSQL cluster using pgvector. Partition vector memory by broker_id so firm-specific naming conventions are recalled accurately without cross-tenant bleed.
  • Exact Header Redis Cache: Compute SHA-256 hashes of row-0 headers. If an identical broker spreadsheet layout is processed again, retrieve 100% of mappings from Redis in < 5ms with zero LLM API or embedding costs.

Category E: Governance, Insurance Regulations & Compliance

Q10: Why is Pandera schema validation superior to traditional Python dictionary checks or pydantic row-by-row iteration in this pipeline?

Evaluation Target: Vectorized validation, memory performance, schema contracts

Model Answer:

Validating large tables (e.g. 50,000 rows × 17 columns = 850,000 cells) by instantiating individual Pydantic model objects per row is computationally expensive, consuming significant memory and taking tens of seconds in Python loops.

Pandera validates the entire DataFrame as a single vectorized columnar structure:

  • Vectorized Speed: Executes column-level null checks, dtype verifications, and ordering constraints in milliseconds using optimized C/Cython routines.
  • Lazy Error Aggregation: Using schema.validate(df, lazy=True), Pandera does not stop at the first error; it collects all schema violations across all columns in a single pass, providing a comprehensive diagnostic report to the user.
  • Strict Invariance: Pandera enforces exact column counts (17), exact column names, and strict column ordering in a single declarative block before any file is serialized to disk.
