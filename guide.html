1. Technology Stack & Design Principles

The system is built on a hybrid deterministic/agentic philosophy: AI and heuristics suggest and map, but strictly whitelisted Python/Pandas functions execute changes with 100% human auditability.

2. System Architecture

The system follows a pipeline-driven architecture divided into five modular layers:

Layer 1: Ingestion
Workbook Processing
OpenPyXL parses Excel/CSV workbooks once, unmerges cells (fill down only), drops notes and totals, and merges all data sheets.
Layer 2: Intelligence
Multi-Agent Cascade
Discovery, cascading Schema Mapping, and Quality Reasoning agents generate confidence-scored proposals.
Layer 3: Human Gate
HITL Approval Barrier
Streamlit review console: anything below 90% confidence (or a high/medium-severity issue) must be decided individually.
Layer 4: Execution
Controlled Transformation
Deterministic transformation whitelist runs approved changes and logs every rename and operation (with rows changed) to an audit trail.
Layer 5: Deliverables
Pandera & Export
Output verified against the exact 17-column schema and field types, exported as Cleaned_SOV.xlsx and Audit_Log.xlsx.
Core Architectural Invariant: The LLM is never permitted to directly alter raw tabular cell data. All data mutations are performed by audited, pure Python functions strictly tied to an approved recommendation ID.

3. The 4-Agent Pipeline in Detail

Agent 1: Sheet Discovery & Header Detection (sheet_discovery.py)

Commercial SOVs frequently arrive with preamble metadata, cover letters, legal disclaimers, or multi-sheet workbooks. This agent scans all sheets and locates the true tabular header row.

  • Multi-Factor Sheet Scoring: 0.35 × header synonym matches + 0.25 × data density + 0.20 × type consistency + 0.20 × row volume.
  • Header Row Search: Scans the first 30 rows, scoring synonym matches, text ratio, fill ratio and numeric data below, to isolate the header row while skipping decorative titles.
  • Merged Cells: Each merged value is filled down its first column only; banners and footnotes merged across columns are never copied into data fields.
  • Classification: Categorizes sheets into PRIMARY, SECONDARY, or REJECT. Every PRIMARY sheet is a data sheet, and all data sheets are merged into one output (e.g. three tabs of SOV_Q8B3.xlsx).

Agent 2: Cascading Schema Mapping (schema_mapping.py)

Maps arbitrary source column headers to the 17 standardized canonical fields using a cascade. Every candidate is scored as 0.45 × name similarity + 0.35 × value-profile fit + 0.20 × method agreement:

Stage 0: Memory
ChromaDB Recall
Nearest past human-approved mapping (similarity > 0.85). Stored confidence, boosted ×1.10 (cap 0.99).
Stage 1: Exact Match
Lexical Matching
Normalized header against field names and 130 curated synonyms. (Name similarity 0.97)
Stage 2: Fuzzy Match
RapidFuzz Token Sort
token_sort_ratio ≥ 75 against names and synonyms; top 5 candidate fields. (score × 0.92)
Stage 3: Semantic
BGE Small Embeddings
Cosine similarity of the header to field names, definitions and synonyms (≥ 0.70); top 5 candidates. (cosine × 0.90)
Stage 4: LLM
Ambiguous Columns Only
Structured JSON decision from masked samples, for columns still unresolved. Always requires review.

Value-Profile Veto: a candidate is rejected when the column's values contradict the field (fit < 0.25), e.g. building numbers as Building Value or longitudes as Country.

Constraint Enforcement: targets are claimed strongest-column-first, so a weak early match cannot block a strong later one, and each target is used once per sheet. Columns from different merged sheets may share a target.

Agent 3: Data Quality Reasoning & HITL Generation (quality_reasoning.py)

Performs statistical profiling, anomaly detection, and human review recommendation synthesis.

  • Deterministic Checks (12): completeness, currency formatting ($ symbols, commas), negative and non-numeric amounts, Year Built range, storey and building counts, sprinkler codes, state codes (incl. V.I.), duplicate references, ZIP format, non-integer integer fields.
  • Quality Scoring: One 0–100 score from mapping coverage × confidence, completeness and issue severity, shared by the report and the UI.
  • LLM Synthesis: The configured LLM writes human-readable explanations from issue counts and masked examples. It may lower but never raise a confidence, and cannot attach operations to column mappings.
  • HITL Review Controls: Underwriters have full control: Approve confirms the mapping; Reject executes in 1 click and drops the source column cleanly from output without prompt friction; Change Target manually assigns the column to another standard field and persists the decision into ChromaDB vector memory as active human feedback (method="human_feedback").
  • Mapping Accuracy KPI: A real-time metric pill is displayed in the top action bar beside the bulk approval button, calculating (predicted_columns_approved / total_columns_predicted) × 100.

Agent 4: Controlled Transformation & Pandera Validation (transformation.py)

Executes approved recommendations with mathematical determinism.

  • Deliverables: Cleaned_SOV.xlsx and Audit_Log.xlsx (exact names) plus timestamped copies; the written file is re-checked for merged cells.
  • Approved Renames & Rejection Drops: Approved column mappings are applied first. Rejected source columns are explicitly dropped from the output DataFrame and logged as column_rejected_dropped. Raw columns that merely happen to carry a target name never reach the output unless approved.
  • Whitelisted Mutations: Strictly limited to strip_currency, to_float, to_int, to_str, to_year_int, to_zip, state_to_abbrev, normalize_sprinkler_code, trim_whitespace, normalize_spaces, normalize_date and flag_for_review (no change).
  • Null Preservation: Missing/blank values stay empty—the system never synthesizes property values. Fractions such as 1.5 storeys are kept, not truncated.
  • Schema Contract: Ensures output has exactly the 17 target columns in the canonical order; numeric Zip cells are formatted 00000.
  • Validation: Pandera checks column presence and order; a type check reports non-numeric or non-integer values in numeric fields.
  • Unclaimed Column Handling: Unmapped source columns are surfaced in the Review tab. The human reviewer can reject them (dropped from output) or manually assign them to any target field. Multiple columns assigned to the same target field are automatically merged into a single cell separated by a space. All decisions are tracked in Audit_Log.xlsx.
  • Audit Logging: One entry per rename, per applied operation, and per rejected/dropped column, recorded before the change is written.

4. Target Schema — The 17 Canonical Fields

Every submitted SOV, regardless of whether it contains 8 columns or 40 columns, is transformed and structured into the 17 standardized commercial property underwriting fields (exact order and names). All fields are nullable: a field with no source column stays empty.

# Canonical Field Name Type Underwriting Purpose Transformation & Validation Rules
1 Reference String Location / Schedule ID Unique location identifier (Loc #, Location ID, Item #). Duplicates flagged for review.
2 Address String Physical Property Address Street address for geocoding and catastrophe accumulation modeling.
3 City String Municipality City name for territorial zoning.
4 State String US State Jurisdiction 2-letter postal abbreviation (e.g. CA, VI); full or dotted names converted by state_to_abbrev.
5 Zip Integer Postal Code 5-digit ZIP (ZIP+4 truncated). 3–4 digit values that lost leading zeros are kept; exported with format 00000.
6 County String Administrative District County jurisdiction.
7 Country String Sovereignty Country code or name, as supplied.
8 Building Value Float Physical Structure Exposure Replacement cost of the building. strip_currency removes $ and commas; negative and non-numeric values flagged.
9 Contents Float Business Personal Property (BPP) Value of equipment, furniture, and inventory. Same monetary checks.
10 BI Float Business Interruption / Time Element Business income or extra expense value. Same monetary checks.
11 Occupancy String Operations / Occupancy Type Usage category (e.g. Office, Retail, Manufacturing, Warehouse) or code.
12 Construction String Construction Class Frame, Joisted Masonry, Non-Combustible, Fire Resistive, or ISO class code.
13 Storeys Integer Building Height / Floors Number of floors; values < 1 or non-numeric flagged; fractions reported, not truncated.
14 Number of Buildings Integer Complex Structure Count Buildings at the location; values < 1 flagged.
15 Year Built Integer Construction Year 4-digit year between 1700 and the current year; to_year_int extracts it from text such as 1980's.
16 Fire Sprinklers (Y/N) String Fire Protection Codes Y, N, Y13, Y(13R); Yes/No/1/0 normalized.
17 Other Float Other Insured Value Other value not covered by Building, Contents or BI. Same monetary checks.

5. Intermediary State Machine & Data Models

The entire lifecycle is modeled in app/schemas/state_models.py via Pydantic models. Each agent works on a deep copy of the state, and the graph checkpoints it as plain JSON, enabling serialization and resume.

Workflow Stages (WorkflowStage Enum)

Stage 0
INIT
File uploaded and session metadata initialized.
Stage 1
DISCOVERED
Sheets scanned, primary table identified, headers extracted.
Stage 2
MAPPED
Source columns mapped to target schema with composite scores.
Stage 3
ASSESSED
Data quality anomalies flagged; recommendations generated.
Stage 4
HUMAN_REVIEW
Underwriter evaluates and confirms proposals in Streamlit UI.
Stage 5
COMPLETE
Transformations applied, validation passed, deliverables exported. (VALIDATING: exported but validation failed; ERROR: stopped with a message.)

7. Putting Into Production & Scaling Strategies

To scale this system from hackathon demo to an enterprise-grade commercial underwriting platform processing tens of thousands of complex property schedules monthly, implement the following architectural enhancements:

A. Microservices Decoupling (API & Worker Separation)

  • FastAPI Core Service: Replace direct Streamlit processing with a high-throughput async FastAPI gateway exposing /api/v1/sov/upload, /api/v1/sov/{id}/status, /api/v1/sov/{id}/approve, and /api/v1/sov/{id}/export.
  • Celery + Redis Task Workers: Offload heavy workbook parsing, embedding generation, and Pandera validations to distributed Celery workers running on containerized worker nodes (AWS ECS / Kubernetes).
  • WebSocket Real-Time Progress: Stream pipeline stage updates (Discovery → Mapping → Quality) to the frontend via WebSockets instead of blocking HTTP requests.

B. Distributed Vector Store & Relational State Management

  • PostgreSQL + pgvector: Replace local embedded ChromaDB with managed PostgreSQL using the pgvector extension. Store both relational session state (audits, recommendations, user approvals) and 384-d semantic column embeddings in a single ACID-compliant database.
  • Tenant Isolation: Partition episodic mapping memory by broker_id or carrier_id so firm-specific synonyms (e.g. Aon vs. Marsh naming conventions) are recalled accurately without cross-tenant bleed.

C. High-Performance Caching & Cost Optimization

  • Exact Header Redis Cache: Cache MD5 hashes of row-0 headers. If an identical broker spreadsheet layout is processed again, retrieve 100% of mappings in < 5ms with zero LLM API or embedding costs.
  • Selective LLM Invocation: Retain the current design where mappings are solved deterministically via Memory, RapidFuzz, and Cosine similarity whenever the values agree. Only route unresolved columns to the LLM Gateway.

D. Enterprise Security, Auditing & Compliance

  • S3 / Azure Blob Storage with KMS Encryption: Store uploaded raw files and finalized Cleaned_SOV.xlsx files in private object stores encrypted at rest via AWS KMS (AES-256).
  • Immutable Tamper-Evident Audit Trails: Export audit log entries with SHA-256 hash chains to satisfy internal model governance and external insurance regulator examinations (NAIC / Lloyd's compliance).
  • PII Redaction: The current masking replaces digits and e-mail addresses but keeps words; add named-entity redaction to strip owner names before any third-party LLM inference.

8. Comprehensive Interview Questions & Technical Deep-Dive

A curated set of challenging questions frequently asked by technical interviewers, system architects, and hiring managers regarding this system's design, algorithmic trade-offs, and implementation details.

Category A: Multi-Agent Architecture & LangGraph Design

Q1: Why did you choose an Agentic / Multi-Agent architecture instead of a single prompt sending the entire spreadsheet to GPT-4o or Claude 3.5 Sonnet?

Evaluation Target: Context window costs, hallucination control, latency, and determinism

Model Answer:

In commercial insurance underwriting, using an LLM as a monolithic end-to-end data transformer is fundamentally flawed for four primary reasons:

  • Hallucination & Numerical Integrity: LLMs are autoregressive token predictors, not execution engines. Asking an LLM to rewrite thousands of rows containing Building Values (e.g. $45,230,000) risks subtle token mutations, row dropouts, or synthetic value fabrication, which creates catastrophic underwriting exposure errors.
  • Context Window & Cost Explosion: Production SOVs easily exceed 10,000 rows. Sending entire raw tables to frontier models consumes millions of tokens, triggering exorbitant API bills and multi-minute response latencies.
  • Separation of Concerns: Our multi-agent system decouples Discovery (structural layout), Mapping (lexical & semantic alignment), Quality Reasoning (business rule audit), and Transformation (deterministic execution). Each agent has a single, verifiable responsibility.
  • Deterministic Sandbox: In our system, the LLM is restricted strictly to an advisory role (reasoning and selecting whitelisted functions). Only pre-validated, pure Python routines ever mutate cell data.

Q2: How does your LangGraph state container enforce immutability and handle state rollbacks on failure?

Evaluation Target: Distributed state design, Pydantic V2 deep copying, error recovery

Model Answer:

Every LangGraph node function in app/agents/ receives a typed SOVState instance and immediately executes state = state.model_copy(deep=True) before performing any mutations. This guarantees that:

  • No agent inadvertently mutates previous stage snapshots via reference sharing.
  • If an unhandled exception or Pandera schema validation failure occurs in Agent 4, the system captures the failure state in state.stage = WorkflowStage.ERROR or WorkflowStage.VALIDATING without corrupting intermediate mapping or profiling states.
  • The human reviewer can interactively adjust, reject, or override recommendations without requiring the system to re-run expensive sheet discovery or vector embedding computations from scratch.

Category B: Schema Mapping, NLP & Vector Retrieval

Q3: Walk me through your 4-Tier Schema Mapping cascade. Why not use vector search for all columns?

Evaluation Target: Latency hierarchies, algorithmic efficiency, semantic false positives

Model Answer:

Vector search is computationally heavier (about 10–20 ms per header on CPU once the model is loaded, versus microseconds for a hash lookup) and is prone to semantic false positives on domain-specific acronyms. Our 4-tier cascade implements a strict efficiency and precision hierarchy:

  • Tier 0 (ChromaDB Memory): Checked first. If a broker previously submitted column "Loc Bldg Identifier" and an underwriter approved it to Reference, memory returns it (similarity > 0.85) with a 1.10× confidence multiplier, provided the column's values still fit.
  • Tier 1 (Exact Normalized Hash): O(1) hash table lookup against 17 canonical names and 130 insurance synonyms, with 0.97 name similarity.
  • Tier 2 (RapidFuzz Token Sort Ratio): Handles minor typos, punctuation differences, and word re-orderings (e.g. "Values - Building" vs "Building Values"). Cutoff 75 (FUZZY_THRESHOLD 0.75).
  • Tier 3 (Dense BGE Embeddings): Cosine similarity using BAAI/bge-small-en-v1.5 (384 dimensions) against canonical names, definitions and synonyms, cutoff 0.70. Handles semantic synonyms like "Time Element" ↔ BI. At 0.60 it also matched unrelated headers (SW, Dept), which is why the threshold was raised.
  • Tier 4 (LLM Gateway): Invoked only for columns that are still unresolved. The LLM receives masked sample values and candidate targets, returning a strictly structured JSON decision that always requires review.

Q4: How do you enforce that each target field is filled by only one column, and why does the order of assignment matter?

Evaluation Target: 1:1 constraints, greedy vs. optimal assignment, collision prevention

Model Answer:

In real-world broker files, several raw columns often look similar to the same target. A workbook may contain both Building (values) and Bldg. (building numbers). Mapping both to Building Value would corrupt the underwriting feed.

The first version assigned targets left to right, so a weak early match blocked a strong later one: in SOV_K4T9.xlsx, Account Name took Reference and the exact synonym Location ID was left unmapped. The current assignment is confidence-ordered (a greedy approximation of optimal matching, not the Hungarian algorithm):

  • Pass 1 scores every column independently.
  • Pass 2 repeatedly commits the pending column with the highest confidence. A column whose target is already taken is re-scored without it and re-queued at its new confidence.
  • The constraint applies per sheet: when several tabs are merged, 2023 Building Value on one tab and Building Value on another may both feed Building Value, because their rows never overlap.
  • A final safety pass demotes any remaining same-sheet duplicate to UNRESOLVED with the reason in its rationale.

Q5: What is "Value Profile Fit" (VPF) and how does it prevent catastrophic mapping errors?

Evaluation Target: Multi-modal signal fusion, data distribution profiling, defensive AI

Model Answer:

Relying purely on column header names is dangerous because brokers use misleading or overloaded labels. For example, a column labeled "State" could contain building status descriptions ("Under Construction", "Vacant") rather than geographic US state abbreviations ("CA", "TX"). Conversely, a column labeled "Coverage 1" might contain dollar amounts ($2,500,000).

The profiling.py module inspects actual cell data:

  • Computes numeric ratio, currency ratio, date/year patterns, 5-digit ZIP codes, and 2-letter postal codes.
  • score_value_profile_fit(profile, target) produces a score from 0.0 to 1.0.
  • VPF enters the confidence formula (0.45 × Sname + 0.35 × Vprofile + 0.20 × Amethod), and it is also a hard veto: if a non-empty column scores below 0.25 for a field, that field is rejected however well the header matches. A column labeled "State" with no state codes and 95% numeric values therefore cannot become State.
  • Real catches: building numbers 1–6 under Bldg. rejected as Building Value; dollar amounts under Building rejected as Number of Buildings; longitudes rejected as Country.

Category C: Data Engineering, Resiliency & Edge Cases

Q6: How do you handle merged cells, forward filling, and multi-tier headers in OpenPyXL?

Evaluation Target: Low-level spreadsheet parsing, Excel object model

Model Answer:

Standard pd.read_excel() places a merged value in the top-left cell and leaves the rest of the range empty. Our unmerge_and_forward_fill() implementation fills it deliberately:

  1. Opens the workbook once using openpyxl.load_workbook(path, data_only=True) to capture calculated formula results; the parse is cached per file and modification time.
  2. Extracts all range coordinates from worksheet.merged_cells.ranges.
  3. For each range, reads the master value at its top-left cell and unmerges the range via worksheet.unmerge_cells().
  4. Writes the master value down the first column of the range only. A vertically merged Loc # belongs to every row it spans; a horizontally merged banner or footnote does not belong in other columns. Copying across columns once turned the footnote "updates in 2018 to 2019" into Zip 20182 and Year Built 2018.
  5. After the header row is applied, footnote rows (a single text cell), totals and whitespace-only rows are dropped.

Q7: You encountered a pandas AttributeError: 'DataFrame' object has no attribute 'str' during production testing. What caused it and how did you resolve it?

Evaluation Target: Real-world debugging, Pandas internal mechanics, DataFrame vs Series slicing

Model Answer:

In broker file SOV_B4ID.xlsx, three separate columns shared the exact same header: "2024 - Increase 10%". In pandas, slicing df[col] returns a pd.Series if col is unique, but returns a 2D pd.DataFrame if col appears multiple times.

Downstream profiling code called series.dropna().astype(str).str.strip(). Calling .str on a DataFrame raises AttributeError because .str is an accessor exclusive to Series.

The Fix:

  • In workbook.py::extract_data_frame(), implemented automatic header deduplication during initial extraction (duplicates become "2024 - Increase 10% (1)", "(2)", …).
  • In profiling.py::profile_column() and schema_mapping.py::map_column(), added defensive type checks: if isinstance(series, pd.DataFrame): series = series.iloc[:, 0].
  • In transformation.py, disambiguated duplicate target columns by calculating non-null counts across candidate slices and preserving the slice with the highest information density.

Category D: Scalability, Productionization & LLM Failovers

Q8: How does your system behave when cloud LLM rate limits (e.g. Groq TPM limits) or network outages occur?

Evaluation Target: High availability, circuit breakers, graceful degradation

Model Answer:

The system implements a multi-provider fallback hierarchy inside app/services/llm/gateway.py:

  • Gateway Client Abstraction: Code interacts with get_llm() rather than calling provider-specific SDKs directly.
  • Provider Failover: The provider in LLM_PROVIDER is tried first. On a rate limit (HTTP 429), timeout or connection error, the gateway tries other Groq models, then the other configured providers: Groq/Gemini only with an API key, local Ollama only when it is the provider or OLLAMA_BASE_URL is set explicitly.
  • Safe Degradation: If every provider fails, the pipeline does not crash. Unresolved columns stay UNRESOLVED and require human review; all deterministic mappings, quality checks and validations still run.

Q9: How would you scale this application to process 50,000 SOVs per day in an enterprise insurance carrier?

Evaluation Target: System design, distributed systems, queuing, database partitioning

Model Answer:

To transition from the current single-instance Streamlit app to an enterprise underwriting fabric:

  • Decouple Frontend & Backend: Expose async REST APIs via FastAPI (e.g., POST /api/v1/sov/ingest, GET /api/v1/sov/{id}/status, POST /api/v1/sov/{id}/decide). Stream real-time stage progress to client SPAs via WebSockets.
  • Distributed Task Workers (Celery + Redis): Enqueue incoming workbooks onto Redis task queues. Stateless Celery worker pods deployed on AWS EKS or ECS handle unmerging, embedding generation, and Pandera validation horizontally.
  • Database Migration (PostgreSQL + pgvector): Replace local ChromaDB with a centralized PostgreSQL cluster using pgvector. Partition vector memory by broker_id so firm-specific naming conventions are recalled accurately without cross-tenant bleed.
  • Exact Header Redis Cache: Compute SHA-256 hashes of row-0 headers. If an identical broker spreadsheet layout is processed again, retrieve 100% of mappings from Redis in < 5ms with zero LLM API or embedding costs.

Category E: Governance, Insurance Regulations & Compliance

Q10: Why is Pandera schema validation superior to traditional Python dictionary checks or pydantic row-by-row iteration in this pipeline?

Evaluation Target: Vectorized validation, memory performance, schema contracts

Model Answer:

Validating large tables (e.g. 50,000 rows × 17 columns = 850,000 cells) by instantiating individual Pydantic model objects per row is computationally expensive, consuming significant memory and taking tens of seconds in Python loops.

Pandera validates the entire DataFrame as a single vectorized columnar structure:

  • Vectorized Speed: Executes column-level presence, nullability and ordering constraints in milliseconds. (Our schema declares no dtypes because cleaned columns can legitimately hold nulls and mixed raw values; a separate vectorizable check verifies that numeric fields hold numbers and integer fields whole numbers.)
  • Lazy Error Aggregation: Using schema.validate(df, lazy=True), Pandera does not stop at the first error; it collects all schema violations across all columns in a single pass, providing a comprehensive diagnostic report to the user.
  • Strict Invariance: Pandera enforces exact column counts (17), exact column names, and strict column ordering in a single declarative block before any file is serialized to disk.
